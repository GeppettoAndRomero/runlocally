# PWA and delivery

How the site works offline, how it updates, how old service workers are retired, and how headers and old URLs are produced. Nothing here is written by hand into the served files; each part is generated and checked in CI.

## Service worker

There is one service worker, `/sw.js`, with scope `/`. It is generated by `@vite-pwa/astro` (Workbox `generateSW`, configured in `astro.config.mjs`). There is no hand-written cache name: Workbox names the cache after its precache and gives every entry a revision.

- **What is precached:** the built pages, the content-hashed files under `/_astro/`, the icons, the manifest, `SECURITY.md`, and the libarchive worker and WASM under `/vendor/libarchive/`. Nothing else is cached at run time: there is no runtime caching, no cross-origin caching and no `navigateFallback`, so each page is served from its own precached HTML.
- **The worker and WASM are a matched pair.** They must come from the same build, so `scripts/pwa-manifest.mjs` gives both entries the same revision (a hash of the two file names and contents) and an integrity hash each. The build fails if one of them is missing or listed twice. A device can therefore never hold a new worker with an old WASM.
- **Pages are precached under their public URLs.** The same script maps each built file to its URL, and fails the build on a page it does not expect or a duplicate.
- **Manifest and icons:** `public/manifest.webmanifest` uses `id: /`, `start_url: /zip/` and `scope: /`; installation opens the Japanese ZIP entry page. Its display mode is `display: standalone`. The icons come from `public/icons/app.svg`; `scripts/gen-pwa-icons.mjs` regenerates the 192 and 512 PNGs (maskable) and the 180px `public/icons/apple-touch-icon.png` from it. The head also links to `public/icons/favicon.svg`. These assets are precached. The 200 KB precache size check counts JS, CSS, and HTML, including the worker's asset list, but excludes the PNG and SVG files themselves.

`scripts/build-meta.mjs` inserts the build SHA into every public HTML after service worker generation and before `scripts/gen-headers.mjs` creates headers. A SHA-only change does not alter precache revisions; changed page content does. Read the current deployed SHA through HTTP without the service worker, rather than from an older tab’s DOM. See [COVENANTS.md](COVENANTS.md) for the deployment check and its limits.

## Registration and old workers

The hub and ZIP pages both mount `PwaStartup`, which displays one installation prompt and one update prompt. The hub loads it as its own island; ZIP renders it inside Workbench. At this stage, the inner `UpdatePrompt` starts registration after the installation event listener is attached.

`src/app/registerSW.ts` runs before it registers anything:

1. It unregisters every service worker whose scope is not `/`, and deletes every cache whose name does not start with `workbox-`. Removing something that another tab has already removed counts as success; only a removal that really fails is an error.
2. It registers `/sw.js` with scope `/`.

Earlier versions of the site used one worker per tool, each under its own path. Two things retire them together:

- the registration code above removes them from a device that opens the new site;
- every old `/<slug>/sw.js` answers **410** (see [Old URLs](#old-urls)). A worker script must never be redirected, and a 410 or 404 when the browser re-checks the script is what lets it discard the registration on its own.

If a registration or removal fails, the page says so and offers a retry; it does not fall back to running with a half-cleaned state.

## Updates

An update is never applied by itself. When a new build is waiting, the page offers "Update now". The button is enabled only when all of these hold, and the reason is shown when one does not:

- no other tab of the site is open (the tabs coordinate with Web Locks and a BroadcastChannel; if the browser cannot check, the update stays pending);
- on the hub, there is no active work; on ZIP pages, nothing is running, including while a dropped file is still being read;
- on ZIP pages, no file is open and no result is listed: the reload would discard both. Saving a result does not clear it from the list, so press Reset first. The prompt says so when this is the reason.

Once the user applies an update the page refuses new input, and the same checks run again right before the reload, so a change of state in between cannot lose work. If it is no longer safe, the new worker still becomes active but the page keeps running, and asks the user to reload after finishing.

The other-tab and coordination checks apply on both hub and ZIP pages.

## Headers and CSP

`scripts/gen-headers.mjs` runs after the build and writes `dist/_headers` (Cloudflare Pages) and `docker/headers.caddy` (self-hosting) from one policy. Do not create `public/_headers`; CI fails if it exists, and `npm run headers:check` fails if the generated files are stale.

- **CSP:** every inline script of every built page is hashed and listed in `script-src` (JSON-LD is data, not script, and is not listed). `script-src` is `'self'`, `'wasm-unsafe-eval'` (only for WebAssembly) and those hashes. `worker-src` is `'self'`. **`blob:` is not allowed for scripts or workers**; if a feature seems to need it, change the feature. The site makes no requests to other origins.
- **Cache-Control:**
  - `/_astro/*` is `immutable` for a year, because the file name contains a content hash.
  - `/vendor/*` is `no-cache` (revalidate every time). Those files sit at fixed paths and must stay a matched pair, so caching them as immutable could leave a device with half of an old and half of a new pair after an update. The service worker precaches them anyway, so this does not affect offline use.
  - `/sw.js` is `no-cache`, so a new build is noticed.
- Other headers: `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` and `frame-ancestors 'none'`.

## Old URLs

`functions/_middleware.js` (Cloudflare Pages Functions) handles URLs of the earlier per-tool sites. Its historical slug table is generated by `scripts/gen-legacy.mjs` from `legacy/slugs.json`; generation rejects duplicate or invalid slugs and a `zip` slug that would collide with the current ZIP routes. `npm run legacy:check` fails when the table is stale (CI runs it).

- Every historical `/<slug>/...` URL, including `/<slug>/ja/` and `/<slug>/sw.js`, and every `/en/<slug>/...` URL answers **410**. So do `/blog/`, `/privacy` and earlier locale roots. There are no 301 redirects from old URLs. A 410 has `Cache-Control: public, max-age=3600`; clients may retain it for up to an hour. Publishing an operation does not revive its old slug.
- Responses on a `*.pages.dev` host carry `X-Robots-Tag: noindex`. That keeps the preview host out of search indexes; it is not access control.

The hub is `/` and `/en/`; the ZIP entry pages are `/zip/` and `/en/zip/`. The sitemap lists these four URLs and the Japanese and English pages for each public ZIP operation: `view`, `extract`, `remove` and `fix-names`, for 12 URLs total. Each page links to its Japanese and English counterpart, and `x-default` points to English. The operation registry controls new ZIP pages and their sitemap entries; `legacy/slugs.json` is a separate historical table. Run `npm run legacy:generate` only when that table changes.

When an operation becomes available, change its `available` flag in `src/i18n/ops.ts`, add its two dictionary entries (see [I18N.md](I18N.md)), add fixtures in `tests/e2e/_covenant-support.ts` and an operation driver in `tests/e2e/_helpers.ts`, then run `npm run build` and `npm run test:e2e` against the build. The e2e checks fail when a published operation lacks a fixture or driver. The new page, sitemap and precache list follow from the public registry; historical URLs remain gone.

## Automated and device checks

CI runs `npm run ci` for the build, unit and component tests, and static egress check. Its separate e2e step runs `npm run test:e2e`. Build before running e2e locally: `playwright.config.ts` serves the build with Wrangler Pages so Functions are included. See [COVENANTS.md](COVENANTS.md) for the test matrix and the remaining device checks.

## Checking it locally

Build, then serve `dist` with the real headers applied:

```sh
npm run build
npx wrangler pages dev dist --port 8788
```

Use one browser profile and always the same address (`http://localhost:8788`, never `127.0.0.1` in between), and do not clear site data between steps, because the checks below rely on what earlier steps left in the browser. Run them in this order.

**1. Headers and old URLs** (any terminal, server running). CI checks CSP responses in `tests/e2e/csp.spec.ts`, the old worker 410 in `tests/e2e/sw-migration.spec.ts`, and policy and legacy routes in `tests/unit/headers-policy.test.ts` and `tests/unit/legacy-middleware.test.ts`. The following commands still check the selected live responses:

```sh
curl -sI http://localhost:8788/ | grep -i content-security-policy        # one line
curl -sI http://localhost:8788/vendor/libarchive/worker-bundle.js | grep -i cache-control   # no-cache
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/zip-viewer/sw.js             # 410
curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" http://localhost:8788/zip-viewer/ja/  # 410, no redirect target
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/en/zip-viewer/    # 410
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/unzip/           # 410
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/en/unzip/        # 410
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/remove-from-zip/  # 410
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/en/remove-from-zip/ # 410
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/zip-filename-fix/ # 410
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/en/zip-filename-fix/ # 410
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/                  # 200 hub
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/en/               # 200 hub
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/zip/              # 200 ZIP entry
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/en/zip/           # 200 ZIP entry
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/format-json/                # 410
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8788/recover-zip/                # 410 historical URL
```

**2. Registration.** Component tests check the hub startup path; the existing e2e covenant checks the root worker, saved assets and control start on ZIP pages. In a new browser profile, open the hub at `http://localhost:8788/` and confirm registration and precache completion before following its ZIP card. Repeat from `/en/` in a separate new profile. DevTools → Application → Service Workers lists one worker with scope `/`. Check that the expected Workbox precache contains the public pages and vendor pair. Other `workbox-` caches may remain; removal applies to cache names without that prefix.

**3. Old workers.** `tests/fixtures/sw/legacy.ts` fixes eight historical scopes: four old tool paths at the root and the same four under `/en/`. `tests/e2e/sw-migration.spec.ts` stages registrations at all eight scopes with the current `/sw.js`, plus two old caches and a Workbox sentinel. In Chromium it checks migration on direct English ZIP entry and on both language hubs, confirming removal on each hub before moving to the English ZIP entry for operation checks. These staged registrations are not captures of old devices. Check a profile with a real old registration separately; otherwise record it as unverified. Retire this by leaving something old behind, then opening the site again.

- Serve a stand-in for an old per-tool worker from a path the middleware does not answer with 410 (a real old path such as `/zip-viewer/sw.js` cannot be used: the middleware refuses it, which is exactly the point). For example, copy this file to `dist/legacy-test/old-sw.js` and restart the server:

  ```js
  const CACHE_NAME = 'old-tool-cache-v1';
  self.addEventListener('install', event => event.waitUntil(
    caches.open(CACHE_NAME).then(cache => cache.put('/old-asset', new Response('old'))).then(() => self.skipWaiting())));
  self.addEventListener('activate', event => event.waitUntil(self.clients.claim()));
  self.addEventListener('fetch', () => {});
  ```

- In the console of `http://localhost:8788/legacy-test/old-sw.js`, register it with a narrow scope, then add a second stray cache:

  ```js
  await navigator.serviceWorker.register('/legacy-test/old-sw.js', { scope: '/legacy-test/' });
  await (await caches.open('other-old-cache')).put('/x', new Response('x'));
  ```

- Open `http://localhost:8788/`. Afterwards the Service Workers list shows only the worker with scope `/`, and non-Workbox caches are removed. Other `workbox-` caches may remain.

**4. Offline.** Chromium e2e checks ZIP pages, reload and the same operations after precache and control. Hub offline navigation still needs a device check. After registration from the hub and control start, stop the server, tick "Offline" in DevTools → Network, reload the hub and follow its ZIP card; then open a ZIP and a 7z file. Check the hub heading and body without waiting for ZIP tool readiness. Every page and the libarchive worker come from the cache. Untick "Offline" and start the server again before the next step.

**5. Update.** Unit and component tests cover deferral and reload decisions. Use two builds with changed page content for the device check; SHA alone does not trigger a precache update. Change some text of a page, run `npm run build` again, restart the server and reload the hub. The update prompt appears there too. Its button stays disabled while a second tab of the site is open. On ZIP pages it also stays disabled while a file is open or a result is listed; press Reset (and close the other tab) to enable it.

**6. Install.** The e2e manifest check and Chromium CDP check cover requirements, while installation and launch remain device checks. On the hub, DevTools → Application → Manifest shows no errors and the installability section lists no blocking issues; in a browser that supports it, the page's install prompt or the browser's own install command works. Confirm one prompt in each language after switching pages. (Lighthouse no longer has a PWA category, so use the Application panel.)
